# Критика MCP-серверов: механизмы, доказательства и ограничения

Дата проверки источников: 2026-09-15.

Статус: справочный обзор. Девять содержательных претензий из инженерных разборов,
исследований безопасности и документации MCP. Это подборка основных аргументов,
а не исчерпывающий каталог проблем.

MCP здесь означает Model Context Protocol. Нужно различать протокол,
реализацию сервера и приложение, которое подключает сервер к модели.
Проблема одного уровня не обязательно присуща остальным.

Связанный материал: [возможная корпоративная ценность Tengu](tengu-enterprise-value.md).

## 1. Дополнительный слой иногда не даёт пользы

**Ситуация:** У сервиса уже есть API и CLI, которыми агент может пользоваться.

**Осложнение:** MCP добавляет ещё один интерфейс: его нужно поддерживать,
документировать и согласовывать с исходным API.

**Вопрос:** Что оправдывает эту сложность?

**Ответ:** Критики считают MCP избыточным там, где агент уже имеет shell и
качественный CLI. Например, получение информации о pull request через `gh`
может закрывать задачу без отдельного сервера. Eric Holmes описывает это
в [«MCP is dead. Long live the CLI», 2026-02-28](https://ejholmes.github.io/2026/02/28/mcp-is-dead-long-live-the-cli.html).

Граница аргумента: удалённые клиенты, централизованные права и совместимость
разных приложений могут оправдывать MCP. Thoughtworks предостерегает именно
от выбора MCP по умолчанию, когда выгоды интеграции не оправдывают сложность.
[MCP by default, 2026-04-15](https://www.thoughtworks.com/radar/techniques/mcp-by-default).

**К чему относится:** выбор архитектуры и среды агента. Преимущество CLI
зависит от наличия shell, подходящих команд и управляемого доступа.

## 2. Обёртка над API ещё не делает инструмент удобным для агента

**Ситуация:** Существующий API автоматически превращают в набор MCP-инструментов.

**Осложнение:** API часто состоит из мелких операций, которые разработчик
связывает кодом. Теперь последовательность, зависимости и ограничения должен
восстановить агент.

**Вопрос:** Почему формально корректная интеграция работает плохо?

**Ответ:** Стандартный формат вызова не заменяет проектирование сценария.
Агент получает технические детали системы, хотя ему требуется законченная
операция. Условный пример: перенос встречи требует найти пользователя,
календарь и событие, проверить доступность и обновить запись. Специально
спроектированный инструмент может объединить эти шаги и проверки.

Именно механическое преобразование API в MCP Thoughtworks поместил в категорию
Hold в ноябре 2025 года. Рекомендация авторов - проектировать инструменты под
агентские задачи поверх существующих API.
[Naive API-to-MCP conversion, 2025-11-05](https://www.thoughtworks.com/radar/techniques/naive-api-to-mcp-conversion).

**К чему относится:** дизайн инструментов. Такая же проблема возможна
у автоматически сгенерированного CLI или плагина Tengu.

## 3. Описания инструментов съедают контекст

**Ситуация:** Агенту подключают несколько серверов с десятками или сотнями
инструментов.

**Осложнение:** Если клиент заранее передаёт модели все описания и схемы
аргументов, они занимают контекст ещё до выполнения задачи.

**Вопрос:** Почему добавление возможностей повышает стоимость и задержку?

**Ответ:** Модель обрабатывает документацию инструментов, большинство которых
сейчас не понадобится. Anthropic описывает пример, где загрузка определений
по необходимости сократила расход со 150 000 до 2 000 токенов. Это пример
конкретной организации работы, не универсальный коэффициент экономии.
[Code execution with MCP, 2025-11-04](https://www.anthropic.com/engineering/code-execution-with-mcp).

MCP не требует загружать весь каталог в контекст. Поиск инструментов и загрузка
по запросу уменьшают проблему. Хранение каталога клиентом и передача каталога
модели - разные события; оценивать нужно фактический контекст модели.

**К чему относится:** управление контекстом в приложении агента. В сравнении
нужно учитывать все обращения к справке и поиску до завершения задачи.

## 4. Передача промежуточных данных через модель расточительна

**Ситуация:** Агент получает данные одним инструментом, обрабатывает их и
передаёт другому.

**Осложнение:** При прямых вызовах большие результаты попадают в контекст,
а затем модель заново генерирует их в аргументах следующего вызова.

**Вопрос:** Зачем использовать модель для обычного копирования и фильтрации?

**Ответ:** Такой цикл расходует токены и время на работу, которую проще
выполнить кодом. Например, таблицу можно отфильтровать в среде исполнения
и вернуть модели только итог.

Cloudflare показывает подход Code Mode: модель пишет программу, которая
связывает MCP-вызовы и сохраняет промежуточные данные вне контекста. Сам
протокол при таком подходе сохраняется.
[Code Mode, 2025-09-26](https://blog.cloudflare.com/code-mode/).

**К чему относится:** организация исполнения. Замена MCP на CLI не устраняет
проблему, если агент продолжает читать каждый полный результат и переписывать
его в следующий вызов. Код также требует подходящей среды исполнения.

## 5. Описание инструмента может стать каналом атаки

**Ситуация:** Модель читает описание MCP-инструмента, чтобы понять его назначение.

**Осложнение:** Недоверенный сервер может встроить туда инструкции, побуждающие
агента читать лишние данные или использовать другой инструмент неправильно.

**Вопрос:** Почему документация способна влиять на безопасность?

**Ответ:** Модель может принять текст внешнего источника за руководство
к действию. Invariant Labs продемонстрировала tool poisoning: вредоносное
описание влияло на поведение агента, включая работу с инструментами другого,
доверенного сервера. В показанных экспериментах интерфейс подтверждения также
скрывал существенные детали вызова. Авторы исследовали и изменение описаний
после первоначального одобрения сервера.
[Tool Poisoning Attacks, 2025-04-01](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks).

Это подтверждение класса атак на исследованные конфигурации. Оно не доказывает
уязвимость каждого современного клиента. Более широкая проблема prompt injection
касается и агентов, использующих API или CLI.

**К чему относится:** доверие к внешнему тексту, полномочия агента и контроль
потоков данных. Смена транспорта сама по себе не решает проблему.

## 6. Подключение сервера означает доверие его коду и обновлениям

**Ситуация:** Пользователь устанавливает сторонний MCP-сервер и предоставляет
ему доступ к рабочему сервису.

**Осложнение:** Сервер может выполнять заявленную функцию и одновременно
совершать скрытые действия. Первоначально нормальное поведение не гарантирует
безопасность обновлений.

**Вопрос:** Были ли реальные случаи такого злоупотребления?

**Ответ:** Да. 25 сентября 2025 года Postmark подтвердил существование
поддельного npm-пакета `postmark-mcp`. После 15 версий автор добавил в `1.0.16`
скрытую отправку копий писем внешнему получателю. Пакет выдавал себя за Postmark,
но официальным продуктом не являлся.
[Официальное сообщение Postmark](https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package).

Это атака через поставляемое ПО, а не ошибка формата MCP. Критика экосистемы
обоснована: удобное подключение интеграции не подтверждает добросовестность
её поставщика.

**К чему относится:** происхождение кода, полномочия и обновления.
Риск сохраняется у CLI-пакетов, зависимостей и серверных плагинов.

## 7. Авторизация остаётся сложной отдельной задачей

**Ситуация:** MCP-сервер действует от имени пользователя и обращается
к другим системам.

**Осложнение:** Нужно согласовать права клиента, сервера и внешнего API,
корректно обрабатывать токены и ограничивать разрешённые операции.

**Вопрос:** Разве стандарт не решает это автоматически?

**Ответ:** Он стандартизирует часть механизмов, но прикладные ограничения
остаются ответственностью реализации. Разрешение подключиться к серверу
ещё не определяет, какие конкретно записи и действия доступны пользователю.

Сопровождающие MCP отмечают, что авторизация занимает у разработчиков большую
часть времени интеграции. [Разбор релиза 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/).
При этом утверждение «у MCP вообще нет авторизации или разграничения прав»
неверно: спецификация предусматривает OAuth, scopes и минимизацию привилегий.
[Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

**К чему относится:** интеграция политик и реализация проверок. Нельзя выводить
наличие или отсутствие прикладного контроля только из названия протокола.

## 8. Эксплуатация и отладка могут стать тяжелее

**Ситуация:** В локальной схеме MCP-клиент запускает сервер отдельным процессом.

**Осложнение:** Появляются дополнительные причины отказа: запуск, зависание,
соединение, транспортные ошибки. Разбор проблемы может потребовать
сопоставления журналов нескольких компонентов.

**Вопрос:** Почему разработчики иногда предпочитают CLI?

**Ответ:** CLI-команду часто проще повторить вручную с теми же аргументами
и непосредственно увидеть результат. Holmes описывает проблемы запуска
MCP-серверов и неудобство разбора транспортных журналов как причины своего
предпочтения CLI. [Eric Holmes, 2026-02-28](https://ejholmes.github.io/2026/02/28/mcp-is-dead-long-live-the-cli.html).

Это практический опыт автора, не доказательство неизбежной нестабильности MCP.
Качество диагностики зависит от конкретного клиента и сервера. Для удалённого
MCP сопровождение процессов может быть централизовано. CLI, обращающийся
к хабу, также зависит от сети и работоспособности сервера.

**К чему относится:** топология и инструменты эксплуатации. Доказательство
преимущества требует одинаковых условий развёртывания и сценариев отказа.

## 9. Ранняя архитектура с сессиями мешала масштабированию

**Ситуация:** Ранние версии MCP строились вокруг инициализации,
двустороннего обмена и сессионного взаимодействия.

**Осложнение:** Состояние соединения усложняло распределение запросов между
экземплярами сервера и восстановление после разрывов.

**Вопрос:** Насколько эта критика актуальна сейчас?

**Ответ:** Для новой версии она существенно ослабла. Спецификация `2026-07-28`
убрала обмен `initialize`/`initialized` и протокольные идентификаторы сессий.
Запросы стали самодостаточными: их можно распределять между экземплярами
сервера без общей протокольной сессии. Старые реализации и затраты на миграцию
остаются. Прикладное состояние также не исчезает вместе с протокольным.
[Официальный разбор изменений](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

**К чему относится:** версия и реализация протокола. Нельзя представлять
неизбежную сессионность как актуальное ограничение любого MCP-сервера.

## Сводный вывод

Наиболее убедительные претензии касаются лишних слоёв интеграции, расхода
контекста, плохо спроектированных инструментов и доверия сторонним серверам.
MCP даёт общий способ подключения; качество, экономичность и безопасность
всей системы требуют отдельных решений.

Часть проблем можно устранить в рамках MCP. Сравнивать Tengu нужно
с конкретными архитектурами и продуктами, включая централизованную
MCP-платформу с хорошим управлением контекстом, правами и интеграциями.
