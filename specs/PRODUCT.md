# Tengu: продуктовое описание, ценность и УТП

Дата: 2026-09-15.

Статус: рабочая продуктовая основа для проработки задач. Текущие возможности,
целевой MVP и предложения по развитию обозначены отдельно. Предложения требуют
проверки на пилоте и детализации перед включением в поставку.

Документ отвечает на вопросы: кому помогает Tengu, какую проблему решает,
почему его выбирать и какой результат должна улучшать следующая задача.
Состав выпуска задаёт [MVP.md](MVP.md), технические решения -
[ARCHITECTURE.md](../ARCHITECTURE.md), статусы и критерии реализации -
[реестр работ](WORK_ITEMS.md) и связанные epics/issues.

## 1. Продукт и позиционирование

Tengu - хаб корпоративных инструментов для AI-агентов. Агент обнаруживает
команды и вызывает их через единый CLI. Центральный сервер исполняет команды
через плагины, обращается к корпоративным системам и хранит их секреты.
CLI обеспечивает общий help, проверку ввода, компактный вывод и понятные ошибки.

### Текущее продуктовое обещание

> Tengu - единый CLI корпоративных инструментов для AI-агентов:
> централизованные интеграции, понятные команды и компактные ответы.

Текущая ценность - удобство подключения и единообразие работы агента.
Рабочая интеграция представлена Jira; переносимость подхода на другие системы
предстоит подтвердить. Экономия токенов на завершённую задачу и снижение
частоты ошибок агента пока не измерены.

### Целевое продуктовое обещание

> Tengu позволяет делегировать агенту корпоративную работу в заданных пределах,
> с понятным согласованием изменений и проверяемым результатом.

Это направление развития. Онлайн-авторизация команд и отдельное человеческое
подтверждение записи ещё не реализованы. Узкие полномочия под поручение и
восстановление после неопределённого результата записи предложены ниже.

## 2. Аудитория и решаемые задачи

| Аудитория | Потребность | Роль Tengu |
|---|---|---|
| Команда AI-платформы | Подключать корпоративные инструменты к нескольким агентским окружениям | Единая точка интеграции и тонкий клиент |
| Разработчик агентов | Давать агенту понятные операции и возможность исправлять ошибки вызова | Общие команды, help, валидация и подсказки |
| Владелец корпоративной системы и команда безопасности | Управлять доступом агентов к данным и действиям | Сейчас серверные секреты; в целевом MVP права на команды и подтверждения |
| Эксплуатация | Устанавливать причину сбоя и находить соответствующий вызов | Серверные события, пользователь, команда, результат и request ID |
| Владелец бюджета AI | Оценивать стоимость успешно выполненной работы | Компактные ответы сейчас; сравнительные измерения в предложенном развитии |

Первая продуктовая проверка - корпоративная команда с одним подключением Jira:
поиск, чтение, создание задач и комментариев, разные права пользователей,
согласование записи и отзыв доступа. Сценарий согласован в [MVP](MVP.md).

## 3. Текущие value propositions

Ценностное предложение описывает пользу пользователю или покупателю.
Техническая возможность служит основанием обещания.

| Ценность | Что уже обеспечивает Tengu | Граница обещания |
|---|---|---|
| Подключать интеграцию централизованно | Плагины на сервере, manifest, тонкие CLI | Клиенты по-прежнему требуют установки, настройки и доступа к серверу |
| Работать с инструментами единообразно | Help, валидация, структурированные ошибки, exit codes и подсказки | Успех конкретной задачи зависит также от модели и качества плагина |
| Использовать корпоративные API без PAT на агентской машине при обычных вызовах | Серверное хранение секретов, разделение по пользователю и инструменту | У клиента остаётся hub-токен; безопасную первичную передачу PAT надо обеспечить отдельно |
| Давать модели необходимую информацию с управляемой детализацией | Выбранные поля, TOON, счётчики, усечение и получение подробностей | Компактность отдельного ответа не доказывает экономию полного сценария |
| Разбирать вызовы из одной точки | Структурированные серверные логи | Логи не равны неизменяемому аудиту или доказательству результата внешней записи |

Основания: [архитектура](../ARCHITECTURE.md), [пример CLI](../README.md),
[контракт логирования](../docs/server-logging.md).

## 4. Текущие продуктовые УТП

УТП - формулировка причины выбрать Tengu среди альтернатив. Ниже приведены
кандидаты для позиционирования; их рыночная уникальность пока не доказана.

### Один CLI для корпоративных инструментов

Агент получает общий способ обнаруживать и вызывать команды. Интеграции
обновляются на сервере; клиент не содержит SDK каждой корпоративной системы.

Ценность для платформенной команды: единая точка подключения и сопровождения
интеграций при нескольких агентских окружениях.

Демонстрация: изменение поверхности плагина становится доступно существующему
CLI через обновление manifest без добавления интеграционного кода в клиент.

### Инструменты помогают агенту исправлять ошибки

Неизвестный флаг сопровождается списком допустимых. Пустой результат обозначен
явно. Для усечённого текста есть способ получить полную версию. Help строится
из того же descriptor, который используется для проверки ввода.

Ценность для разработчика агента: готовая информация для следующего корректного
вызова. Влияние на число повторных вызовов проверяется на сценариях.

Демонстрация: неверный флаг, пустая выборка и длинная задача Jira;
в каждом случае вывод позволяет определить следующий шаг без внешней документации.

### Компактные ответы с управляемой детализацией

Списки содержат поля для выбора следующего действия. Подробности запрашиваются
отдельно. Счётчики и подсказки объясняют полноту результата.

Ценность для владельца бюджета: возможность сократить контекст без потери
информации, нужной для выполнения задачи. Процент экономии публикуется после замеров.

Демонстрация: одинаковая задача через полный API-ответ и через Tengu;
сравниваются правильность результата, все вызовы и суммарные токены.

## 5. Ценность целевого корпоративного MVP

В [EPIC-03](epics/epic_03_external_authorization.md) запланированы актуальная
проверка прав перед исполнением и отзыв доступа. Контракт существующего внешнего
сервиса политик остаётся TBD; выбор провайдера здесь не фиксируется.

В [EPIC-01](epics/epic_01_safe_external_mutations.md) запланировано подтверждение
точной мутации человеком с отдельным credential, недоступным агенту. Подтверждение
связано с пользователем и параметрами операции, ограничено сроком и одноразово.
При исполнении права проверяются повторно, в том числе после подтверждения.

Продуктовая ценность этой связки: разрешать полезную запись в корпоративные
системы с проверяемыми границами доступа и человеческого согласования.
Авторизация, подтверждение и результат внешней операции - разные проверки.
Права Jira продолжают действовать независимо от решения Tengu.

## 6. Предложения для усиления продукта

Следующие направления являются гипотезами развития. Они не включаются
автоматически в текущий MVP и не меняют уже согласованные критерии issues.

### Ограниченные полномочия под конкретное поручение

**УТП:** «Выдавайте агенту доступ ровно на порученную работу».

Пример: создавать задачи только в проекте ABC, максимум пять, до конца дня;
разрешено менять описание, запрещено менять исполнителя.

- Добавить ограничения по объектам, параметрам, сроку и количеству операций.
- Связать ограничения с внешними политиками и проверять их на сервере.
- Сохранить разделение прав пользователя и более узких полномочий поручения.
- Определить семантику квот при конкуренции и неопределённом результате записи.

Ценность: больше полезной автономной работы при узких границах доступа.
Проверка: разрешённые сценарии завершаются; выход за каждый предел блокируется
до внешнего вызова, включая параллельные запросы.

Это расширение EPIC-03: объектные ограничения и полномочия поручений выходят
за текущую границу MVP. Гарантии относятся к операциям, проходящим через Tengu.

### Подтверждение понятного изменения

**УТП:** «Человек видит, какое изменение разрешает агенту».

Основа - подтверждение точных аргументов из EPIC-01. Предлагаемое усиление:
описание бизнес-смысла, diff «было / станет», проверка версии объекта перед
записью там, где внешний API поддерживает такое условие.

Ценность: осмысленное согласование без разбора технического запроса.
Проверка: подмена параметров и несовместимое изменение исходного состояния
приводят к отказу и новому согласованию.

Preview объясняет ожидаемое изменение. Полноту отражения побочных эффектов и
защиту от изменения объекта между проверкой и записью нужно определять для
каждой интеграции; универсальная гарантия не заявляется.

### Управление неопределённым результатом записи

**УТП:** «После обрыва связи агент знает безопасный следующий шаг».

Добавить ID операции и состояния «выполнено», «отклонено», «результат неизвестен».
Предусмотреть проверку фактического результата во внешней системе и применение
idempotency keys там, где API их поддерживает.

Ценность: меньше дублей и ручных расследований после сбоев.
Проверка: обрыв после внешней записи не приводит к слепому повтору;
агент получает подтверждённый результат либо явную неопределённость и способ
её разрешения.

Отсутствие дублей для произвольного API не гарантируется. Развитие должно
сохранить правило EPIC-01: после использования approval и неопределённого
исхода автоматический повтор мутации запрещён. Сверка результата сама по себе
не даёт разрешения на новую запись.

### Измеримая надёжность инструментов для агентов

**УТП:** «Качество интеграции проверено на рабочих задачах».

Подготовить сценарии для каждого плагина: поиск, выбор объекта, исправление
ошибки вызова, запись и восстановление после сбоя. Сравнивать Tengu с прямым
API и выбранным MCP-инструментом при одинаковых данных, правах и критериях успеха.

Ценность: покупатель получает проверяемое основание для выбора продукта.
Артефакт поставки - воспроизводимый отчёт, связанный с версией интеграции.

Измерять:

- долю успешно завершённых задач;
- число вызовов и исправлений;
- суммарные токены и стоимость на завершённую задачу;
- время выполнения и вмешательства человека;
- блокирование запрещённых действий, отдельно от функционального успеха.

Фиксировать модель, агентское окружение, версии инструментов и условия запуска.
Учитывать discovery, help, повторные вызовы и неудачные попытки. Порог успеха
выбирать по базовым замерам пилота, без заранее обещанного процента улучшения.

## 7. Конкурентное отличие и роль MCP

MCP задаёт протокол взаимодействия. Tengu объединяет интерфейс агента,
интеграции и правила исполнения в продукт. MCP-сервер может использовать
центральный Vault, компактные ответы, внешние политики и подтверждения.

Самостоятельная уникальность следующих свойств не предполагается: единый хаб,
серверные секреты, TOON, stateless-вызовы, наличие авторизации и адаптация tools.
Например, [agentgateway](https://agentgateway.dev/docs/standalone/latest/documentation/configuration/security/mcp-authz/)
документирует авторизацию MCP, а
[FastMCP](https://gofastmcp.com/servers/transforms/tool-transformation) -
преобразование схем и поведения инструментов. Источники проверены 2026-09-15;
это ориентиры позиционирования, а не исчерпывающий обзор рынка.

Отличие Tengu следует доказывать сочетанием удобства, контроля исполнения и
качества завершения рабочих задач. Сам по себе собственный транспорт не
обосновывает выбор продукта.

MCP-вход к общему исполнителю - возможный способ расширить аудиторию.
При его добавлении CLI и MCP должны проходить одинаковые серверные проверки
прав, секретов и подтверждений. Это предложение вне текущего MVP.

Дополнительный контекст: [сравнение инструментов](../docs/mvp-tools-comparison.md).

## 8. Приоритеты и применение при проработке задач

Рекомендуемый порядок:

1. Завершить запланированные права и подтверждения, сохраняя состав [MVP](MVP.md).
2. Параллельно собрать базовые измерения на существующих Jira-сценариях.
3. По результатам пилота детализировать ограниченные поручения, понятные preview
   и восстановление после неопределённых записей.
4. Расширять интеграции и добавлять MCP-вход при подтверждённой потребности.

При проработке задачи использовать следующие поля как опору:

- **Пользователь и проблема:** кто сталкивается с ограничением, в каком сценарии.
- **Продуктовая ценность:** какую ценность или УТП из этого документа усиливает задача.
- **Наблюдаемое изменение:** что пользователь сможет сделать после поставки.
- **Проверка результата:** сценарий приёмки и метрика, если её можно измерить.
- **Статус и границы:** развитие текущего продукта, часть MVP или проверка гипотезы;
  зависимости и явно исключённая работа.
- **Основание приоритета:** данные пилота, обязательство MVP, устранение сбоя
  или проверка продуктовой гипотезы.

Техническая задача может поддерживать ценность косвенно через надёжность,
совместимость или безопасность. В таком случае описать конкретный сбой или
ограничение, которое она устраняет, вместо искусственного нового УТП.

Список предложений не является обязательством реализовать все направления.
При изменении позиционирования обновлять этот документ; при изменении состава
поставки согласованно обновлять MVP и связанные issues. Статусы реализации
проверять по issue-файлам, а не по дате продуктового описания.
