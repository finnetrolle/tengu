## Результат

Агент свободно выполняет read-only команды Tengu, но создание, изменение или
удаление данных во внешней системе происходит только после отдельного
человеческого подтверждения точной операции.

Неоднозначная просьба создать «задачу» в контексте репозитория не считается
разрешением на создание Jira issue. При наличии локального адаптера
`specs/WORK_ITEMS.md` такая просьба относится к `specs/`, пока пользователь
явно не назвал внешнюю систему.

## Нормативные требования

- **R1. Локальная семантика задачи.** В репозитории с
  `specs/WORK_ITEMS.md` слова «задача» и «issue» без явно названной внешней
  системы означают локальный work item в `specs/`.
- **R2. Подтверждение перед мутацией.** Перед каждой внешней мутацией агент
  показывает систему, объект, точный эффект и команду без секретов, затем ждёт
  подтверждения пользователя именно этой операции.
- **R3. Непереносимость подтверждения.** Подтверждение одной операции нельзя
  использовать для другой команды, аргументов, пользователя или повторного
  выполнения.
- **R4. Машиночитаемый эффект.** Каждый `CommandDescriptor` объявляет эффект
  `READ`, `WRITE` или `DELETE` и policy `NONE` или `REQUIRED`.
- **R5. Безопасный default.** `WRITE` и `DELETE` обязаны иметь
  `confirmationPolicy=REQUIRED`; некорректный descriptor не регистрируется.
- **R6. Серверное enforcement.** Сервер не вызывает плагин для команды с
  обязательным подтверждением без действующего approval, привязанного к digest
  точного запроса.
- **R7. Отдельная approval authority.** Подтверждение выпускается credential,
  недоступным агенту и отличным от обычного hub token.
- **R8. Ограниченный lifecycle.** Approval имеет TTL 10 минут, используется
  один раз и атомарно переходит через `PENDING`, `APPROVED`, `CONSUMED` или
  `EXPIRED`.
- **R9. Безопасный отказ.** Истёкший, повторно использованный или не
  соответствующий запросу approval приводит к отказу до вызова плагина.
- **R10. Совместимость чтения.** Read-only команды и их текущие payload,
  пагинация, auth и exit codes не меняются.
- **R11. Нет интерактивного prompt в агентском CLI.** CLI возвращает
  структурированный preview и завершает процесс; подтверждение выполняется
  отдельным human-owned каналом.

## Нормативная модель подтверждения

Первый вызов команды с `confirmationPolicy=REQUIRED` только подготавливает
операцию. Сервер валидирует запрос, вычисляет digest, создаёт pending approval и
возвращает redacted preview. Плагин не вызывается.

Approval выполняется через отдельный endpoint и approver credential, которого
нет в конфигурации агента. После approval агент повторяет ту же команду с
`approvalId`. Сервер повторно валидирует запрос, сравнивает digest, атомарно
поглощает approval и только затем вызывает плагин.

Изменение любого аргумента требует нового подтверждения. После consume,
expiration или рестарта in-memory approval store требуется подготовить и
подтвердить операцию заново. Это безопасный отказ, а не основание для
автоматического выполнения.

## Критерии завершения epic

- [ ] Все R1-R11 покрыты хотя бы одной дочерней issue и не противоречат друг
  другу.
- [ ] Все три дочерние issue имеют статус `Done` и их проверки завершены
  успешно.
- [ ] Read-only Jira и status flows проходят без дополнительного подтверждения.
- [ ] `issues create`, `issues comment`, `auth login`, `auth logout` и новые
  mutating commands не достигают `ToolPlugin.invoke` без approval.
- [ ] Изменение command path, args или flags после approval отклоняется до
  вызова плагина.
- [ ] Approver credential отсутствует в agent CLI config, manifest, logs и
  invoke payload.
- [ ] `./gradlew build`, `bash scripts/e2e.sh` и `git diff --check` завершаются
  успешно после интеграции всех дочерних изменений.
- [ ] `ARCHITECTURE.md`, protocol/server/CLI README и manifest version отражают
  итоговый контракт.

## Не входит

- Универсальный workflow engine для произвольных многошаговых операций.
- Подтверждение read-only команд.
- Автоматическое одобрение на основании текста prompt или флага `--yes`.
- Выдача approver credential агенту, skill или Tengu plugin.
- Web UI для очереди approvals; первая версия предоставляет HTTP seam и
  human-owned CLI-команду.
- Долговременное хранение pending approvals между рестартами сервера.
- Undo внешней операции после её успешного выполнения.
- Изменение семантики конкретных Jira-команд, кроме подключения общей policy.
