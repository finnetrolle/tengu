# Tengu: состав MVP и порядок выполнения задач

Дата: 2026-09-10.

Статус: рабочий проект состава и порядка поставки. Цель MVP согласована;
интеграция авторизации отмечена `TBD` по решению пользователя. Существующие
issues сохраняют свои контракты и статусы. Новая декомпозиция не опубликована.

## Цель

Следующий MVP предназначен для корпоративного пилота с внешней авторизацией
и контролем доступа. Реализованный MVP 0.1.0 из `ARCHITECTURE.md` является базой.

Предлагаемый пилотный сценарий: команда работает с одним подключением Jira через
Tengu. Один пользователь может читать задачи, другой также создавать задачи
и комментарии. Сервер проверяет право на команду во внешнем сервисе. Для записи
дополнительно требуется человеческое подтверждение точной операции. Оператор
может отозвать доступ и диагностировать вызов по серверным логам.

Это критерий выпуска: завершение Jira, approvals и логирования без внешней
авторизации даёт промежуточную поставку, но не завершает корпоративный MVP.

## Состав MVP

| Работа | Решение в предлагаемом составе | Результат |
|---|---|---|
| Существующие CLI, protocol, TOON, Jira-плагин и SecretsStore | Использовать как базу | Discovery, help, чтение, создание и комментарии через существующий путь CLI -> сервер -> Jira |
| [EPIC-03: Внешняя авторизация](epics/epic_03_external_authorization.md) | Обязательно; интеграция `TBD` | Проверка прав, отзыв, блокировка пользователя, безопасный отказ |
| [EPIC-01: Подтверждение внешних мутаций](epics/epic_01_safe_external_mutations.md) | Все три дочерние issues | Metadata эффекта, правила агента, prepare/approve/invoke |
| [TNG-03: JSON-логи в STDOUT](issues/issue_03_server_stdout_logging.md) | Включить | Пользователь, команда, длительность, результат и request ID |
| [TNG-01: Сохранение ORDER BY](issues/issue_01_preserve_jira_jql_ordering.md) | Включить | Исправленный существующий сценарий поиска Jira |
| Подготовка и совместная приёмка пилотного стенда | Обязательный результат; отдельную issue оформить после уточнения среды | Воспроизводимый запуск, выдача/отзыв доступа и проверка сценария с Jira |

Управление собственным Jira PAT требует отдельного действия в будущей матрице
прав: право чтения Jira не должно автоматически запрещать подключение своего
PAT. Эффект `WRITE` и разрешение на запись бизнес-данных не являются одной
классификацией. Семантика approvals для auth-команд сохраняется по EPIC-01.

| [EPIC-02: OpenAPI](epics/epic_02_openapi_tools.md) | Подключение новых API не требуется для доказательства корпоративного контроля доступа на существующей Jira |

Также за пределами предлагаемого MVP: объектные ACL для отдельных Jira issues,
собственная панель политик, новый policy engine, web UI approvals, durable
approval store, несколько реплик Tengu и автоматизация произвольных workflows.
Ограничения Jira PAT продолжают действовать независимо от решения Tengu.

## Авторизация: TBD

Подтверждённый контекст:

- В организации есть Keycloak.
- Есть отдельный сервис, в котором задаются политики для инструментов системы.
- Пользователь предоставит этот сервис позже. До этого интеграцию не выбирать
  и не объявлять готовой к реализации.

`TBD` относится к провайдеру и его runtime API, способу подтверждения личности
и передачи её сервису, выдаче credential агентскому CLI, матрице действий и
ресурсов, сроку отзыва, timeout и аудиту. Не подразумевает отказ от EPIC-03.

Сохраняются уже заданные требования EPIC-03:

- онлайн-решение перед исполнением чтения и записи, без межзапросного кэша allow;
- доверенный субъект и серверная привязка команды к действию/ресурсу;
- отказ до плагина при deny, неизвестном разрешении, timeout и ошибке провайдера;
- повторная проверка прав при исполнении после approval;
- проверка отзыва с прежним токеном и отдельная проверка блокировки пользователя.

После получения сервиса: изучить контракт, проверить его на двух пользователях,
уточнить решения, затем декомпозировать EPIC-03. В результате должны появиться
сквозные issues с реальным адаптером, проверяемым allow/deny, отзывом прав и
совместной работой авторизации, approvals и аудита. До этого оценки и дочерние
ID не фиксируются. Новый SSO flow в CLI автоматически в состав не добавляется.

## Карта MVP

```text
Корпоративный пилот
+-- Пользовательский сценарий
|   +-- найти и прочитать Jira issue
|   +-- создать issue или комментарий
+-- Контроль доступа: EPIC-03, интеграция TBD

+-- Эксплуатация
    +-- JSON-логи: TNG-03
    +-- пилотный стенд и совместная приёмка
```

## Порядок выполнения

Рекомендуемый порядок при одном исполнителе:

| Шаг | Работа | Проверяемый результат |
|---|---|---|
| 1 | TNG-01 | Пользовательская сортировка JQL сохраняется; существующие фильтры работают |
| 2 | TNG-01-01 | Проектные правила однозначно различают локальные задачи и внешние мутации |
| 3 | TNG-03 | Сервер пишет JSON-логи и проходит предусмотренную контейнерную проверку |
| 4 | TNG-01-02 | Manifest и help показывают effect/policy; registry отклоняет некорректные сочетания |
| 5 | TNG-01-03 | Мутация не достигает плагина без exact approval; replay и подмена отклоняются |
| 6 | EPIC-03 после снятия TBD | Работают актуальные права и их отзыв, включая исполнение после approval |
| 7 | Совместная приёмка стенда | Пилотный сценарий подтверждён в согласованном окружении |

Шаг 6 можно уточнять раньше, если появится контракт сервиса. Положение в таблице
не превращает предпочтительный порядок в технический блокер.

Текущий frontier по issue-файлам: `TNG-01`, `TNG-01-01`, `TNG-01-02`.
TNG-03 завершена; приёмка логирования отражена в её closure ledger.
Их можно брать без решения по авторизации. При нескольких исполнителях работа
возможна параллельно в отдельных ветках; изменения общих серверных маршрутов,
lifecycle и тестов интегрировать последовательно. Исполнители этим планом
не запускаются.

Существующие жёсткие зависимости:

```text
TNG-01-02 -> TNG-01-03 -> TNG-02 (предлагается после MVP)
```

Для завершения корпоративного сценария записи нужны одновременно EPIC-03
и TNG-01-03. TNG-03 рекомендуется выполнить до изменений маршрутов approvals
и авторизации, чтобы эти изменения сразу учитывали формат логов. Это удобный
порядок интеграции, а не новый блокер TNG-01-03.

## Как закрывать одну задачу

1. Взять Ready issue с завершёнными блокерами и обозначить `In progress`.
2. Реализовать один заявленный результат в отдельной ветке и обозримом PR.
   Не добавлять смежные возможности в объём взятой issue.
3. Выполнить acceptance checks issue и regression tests. Изменения поведения
   CLI/server проверить через E2E; документацию обновить вместе с контрактом.
4. Перед интеграцией пройти требуемые build/tests/Detekt, Windows cross-compile
   и Linux E2E; для TNG-03 также предусмотренную проверку логов контейнера.
5. После завершения синхронно обновить issue, epic и реестр WORK_ITEMS.
   Источник статуса остаётся issue-файл.

Новые issues EPIC-03 оформлять сквозными сценариями после прояснения контракта.
Предполагаемые блоки внутри задачи не публиковать отдельными горизонтальными
задачами только по названиям модулей.

## Приёмка MVP

- Пользователь с правом чтения получает данные; запрещённая запись не вызывает плагин.
- Разрешённое создание issue и комментария требует подтверждения точного запроса.
- Подмена, чужой, просроченный и использованный approval отклоняются; один approval
  допускает максимум один вызов плагина при конкурентном исполнении.
- Отзыв действует с прежним credential в согласованный срок; блокировка
  пользователя проверена отдельно. Отзыв после approval также запрещает исполнение.
- Разрешение для одного подключения не открывает другое; собственные PAT
  пользователей изолированы. Второе подключение можно проверить независимой fixture.
- При сбое провайдера команда не исполняется; клиент различает запрет и сбой проверки.
- Логи связывают пользователя, команду и итог. Аудит решения о доступе добавляется
  в рамках EPIC-03; секретные credentials не попадают в записи.
- Проходят проверки проекта, новые E2E на независимых HTTP fixtures и интеграция
  с реальным провайдером. Проверки внутренних mocks не заменяют эту интеграцию.
- На выделенных тестовых объектах реальной Jira пройден согласованный пилотный
  сценарий. Оператор может воспроизвести запуск, выдачу/отзыв доступа и диагностику.

Для приёмки остаётся согласовать параметры, явно отмеченные TBD в авторизации,
и среду стенда. Это не готовое к автономному выполнению задание на развёртывание.

## Стыки существующих задач

- TNG-02 задаёт увеличение manifestVersion с 4 до 5, хотя её блокер уже меняет
  manifest. При подготовке к реализации заменить фиксированные числа на
  увеличение актуальной версии после предыдущих изменений.
- TNG-03 перечисляет текущие маршруты. При добавлении prepare/approve endpoints
  согласовать новые значения маршрутов, ошибки и audit events с её контрактом;
  владельцы изменений соответственно TNG-01-03 и EPIC-03.
- TNG-01-01 меняет только AGENTS.md репозитория. Техническая гарантия для
  пользователей установленного Tengu обеспечивается TNG-01-03 на сервере.
- Текущий docker-compose.yml использует dev-Vault. Подготовка корпоративного
  стенда должна определить хранилище секретов, HTTPS и владельца эксплуатации.

## Оценка

Из предлагаемого состава уже оценены EPIC-01 в 4.5-8 инженерных дней
и TNG-01 в 1 день. Итого 5.5-9 дней только для этой части.

TNG-03, EPIC-03, подготовка стенда и совместная приёмка в эту сумму не входят.
Календарный срок MVP пока не обоснован. TNG-02 добавит существующую оценку
в 2 дня, если её решат включить в MVP.

Следующая реализация: TNG-01. Следующее уточнение авторизации: после предоставления
пользователем описания сервиса политик. Следующий документальный шаг после
согласования состава: оформить недостающую работу по пилотному стенду и,
когда снят TBD, дочерние issues EPIC-03.
