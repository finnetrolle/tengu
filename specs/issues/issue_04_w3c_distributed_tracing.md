# TNG-04: W3C-трассировка вызовов Tengu CLI и сервера

- **ID:** `TNG-04`
- **Тип:** Issue
- **Статус:** Draft
- **Связана с:** [TNG-03: Серверные логи в STDOUT](issue_03_server_stdout_logging.md)
- **Зависимости:** порядок реализации с TNG-03 уточняется при проработке
- **Оценка:** после уточнения реализации для Kotlin/Native

## Цель и подтверждённая гарантия

Вызов Tengu имеет трассу участка CLI, сервер и исходящие обращения сервера.
Наличие внешнего контекста определяет родителя, но не саму возможность
создать трассу Tengu:

1. Если CLI получает валидный внешний W3C-контекст, продолжает эту трассу
   и передаёт контекст серверу.
2. Если внешнего контекста нет, CLI начинает новую трассу своего вызова.
3. Если доступен идентификатор сессии агента, он сохраняется отдельным
   атрибутом для группировки нескольких трасс.

Без передачи контекста агентом участок с вызовом LLM не является частью
трассы Tengu. Нельзя вычислять trace ID из session ID и объявлять это
восстановлением трассы агента или создавать вымышленного родителя.

Пользователь согласовал отдельную задачу трассировки при интервью по TNG-03.
Настоящий файл сохраняет принятый контракт и открытые решения; он не готов
для автономной реализации.

## Ответственность

- CLI принимает внешний контекст, создаёт spans своего вызова и передаёт
  контекст исходящих HTTP-запросов серверу.
- Сервер создаёт собственные spans и дочерние spans исходящих обращений
  к Jira и Vault. Нельзя обещать spans внутри сторонних Jira/Vault, если
  сами системы не инструментированы; наблюдаем исходящий клиентский участок.
- Логи сервера связываются с действующим контекстом через реальные trace ID
  и span ID. Parent ID принадлежит модели span; нельзя переименовывать
  входящий parent ID в собственный span ID сервера.
- Нужны создание, завершение и экспорт span data. Одни поля в JSON-логах
  не считаются реализацией распределённой трассировки.
- Интеграции с конкретными агентами и развёртывание collector/backend
  требуют отдельного определения границ. Не устанавливать agent hooks
  или plugins в ходе обычного вызова Tengu.

## Проверенный контекст

- CLI является Kotlin/Native для Linux, Windows и macOS; сервер является
  JVM/Ktor. Нельзя выбирать JVM-only библиотеку для CLI или добавлять
  зависимость CLI от `:toolkit` и интеграционных плагинов.
- `cli/.../ServerClient.kt` выполняет `fetchManifest` и `invoke` через Ktor;
  настроен HTTP timeout 30 секунд, клиент закрывается через `AutoCloseable`.
- `cli/.../CliRuntime.kt` читает кэш и при необходимости загружает manifest;
  `fail` завершает процесс через `exitProcess`. Это существенный путь для
  завершения spans и сброса экспортёра.
- `cli/.../Main.kt` обрабатывает `-v`, `-V`, `--version` до загрузки Clikt/Ktor.
  AXI требует сохранить этот fast path, формат stdout и exit codes.
- `server/.../Main.kt` собирает общий HTTP-клиент и запускает Ktor CIO;
  маршруты и выполнение плагинов находятся в `server/.../ServerDeps.kt`.
- Сейчас в репозитории не обнаружены обработка W3C-контекста или MDC.

## Исследование границы агент/CLI

Проверено 2026-09-09:

- W3C Trace Context определяет `traceparent` и `tracestate`; входящий
  `parent-id` обозначает span вызывающей стороны.
- OTel описывает перенос контекста через environment carriers, включая
  нормализацию ключа `traceparent` в `TRACEPARENT`. Статус этого документа
  на дату проверки: `Release Candidate`; это не доказательство автоматической
  поддержки любым агентом.
- В окружении дочерней команды текущей сессии Codex обнаружены переменные
  `CODEX_THREAD_ID` и `CODEX_SESSION_ID`, но нет trace/span/OTel-переменных.
  Значения не сохранялись. Это наблюдение конкретного окружения, а не
  переносимый публичный контракт Codex.
- Проверенная документация Codex описывает политику окружения дочерних
  команд и собственный OTel-export с conversation ID, но не устанавливает
  автоматическую передачу активного W3C-контекста в shell.
- OpenCode документирует hook `shell.env` для добавления переменных
  окружения. Доступ к активному внутреннему span агента нужно исследовать
  отдельно; наличие hook этого не доказывает.

## Открытые решения

1. Точные границы spans: вызов CLI, manifest refresh, HTTP-попытки, invoke,
   исходящие Jira/Vault; охват локальных команд, cache-only путей и ошибок
   до сетевого вызова. Для `--version` сохранить fast path.
2. Контракт внешнего контекста: carrier, precedence, validation, отсутствие
   и некорректные значения, `tracestate`, flags, sampling. Не вводить
   произвольную обработку W3C вместо проверенной реализации.
3. Поведение сервера для прямого HTTP-клиента без CLI и для недоверенного
   входящего контекста; изоляция при параллельных запросах и отмене.
4. SDK/библиотеки и экспорт spans на всех поддерживаемых Native-таргетах;
   канал, endpoint, конфигурация, секреты экспортёра, совместимость версий.
   Не смешивать telemetry с AXI-данными в stdout CLI.
5. Идентификатор сессии: общий входной контракт, допустимые источники,
   формат, границы доверия и атрибуты. Адаптеры Codex/OpenCode пока
   не объявлены обязательной реализацией.
6. Shutdown/flush, sampling, отказ экспортёра, backpressure, влияние
   короткоживущего процесса CLI; явно определить смысл гарантии создания
   трассы и отдельно условия её записи и доставки.
7. План интеграции с TNG-03: владелец добавления trace/span-полей в логи,
   порядок реализации и отсутствие фиктивных ID до создания spans.
8. Исполнимый E2E fixture: Native CLI, сервер, mock upstream и получатель
   экспортированных spans; конечная матрица сценариев и независимый oracle.

## Направление проверки

В окончательной issue нужны отдельные evidence contracts для продолжения
заранее заданного родителя, создания новой трассы, связей между CLI/server/
исходящим запросом, ошибок и отмены, изоляции параллельных вызовов,
корреляции логов, сохранения stdout/exit codes и завершения Native-процесса.
Проверять реальные экспортированные spans через независимый получатель,
а W3C-заголовки через mock HTTP endpoint. Конкретные fixtures и команды
ещё не выбраны, поэтому статус остаётся `Draft`.
